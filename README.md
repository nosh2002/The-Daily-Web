# The Daily Web

מערכת אינטרנטית לניהול, עריכה ופרסום חדשות - פרויקט גמר בקורס פיתוח אפליקציות
אינטרנטיות (סמסטר קיץ), הבנוי לפי מסמך הדרישות: Node.js + Express בתבנית MVC,
MongoDB + Mongoose, EJS לרינדור בצד השרת, ו-Vanilla JavaScript בצד הלקוח.

> **הערה חשובה לפני ההגנה:** מסמך הדרישות קובע במפורש שמותר להיעזר בכלי בינה
> מלאכותית בפיתוח, אך **כל סטודנט חייב להיות מסוגל להסביר כל שורת קוד** בהגנה.
> קוד זה נכתב בעזרת כלי AI כנדרש - השתמשו בו כבסיס, אך עברו על כל קובץ, הבינו
> אותו לעומק, והתאימו אותו לעצמכם (במיוחד: תוכן הכתבות/שמות/ניסוחים) לפני
> ההגשה. חלוקת הקבצים בין חברי הקבוצה בגיט (commits אמיתיים של כל אחד/ת על
> החלקים שהוא/היא הפנימו) היא חלק מהדרישה, לא רק פורמליות.

## דרישות מקדימות

- Node.js גרסה 18 ומעלה (`node -v`)
- מסד נתונים MongoDB פועל **מקומית** על המחשב שלכם. שתי דרכים מומלצות:
  - **התקנה מקומית**: הורידו מ-<https://www.mongodb.com/try/download/community>
    לפי מערכת ההפעלה שלכם, התקינו והריצו את השירות (`mongod`). ברוב ההתקנות
    השירות עולה אוטומטית וממשיך לרוץ ברקע (ב-macOS דרך Homebrew:
    `brew install mongodb-community` ואז `brew services start mongodb/brew/mongodb-community`).
  - **MongoDB Atlas (ענן, חינמי)**: אם אינכם רוצים להתקין מקומית, אפשר ליצור
    cluster חינמי ב-<https://www.mongodb.com/atlas> ולהשתמש בכתובת החיבור
    (connection string) שהוא נותן, במקום הכתובת המקומית.
- מפתח API חינמי מ-[OpenWeatherMap](https://openweathermap.org/api) (לא חובה
  כדי שהאתר יעבוד - בלי מפתח פשוט יוצג "מזג האוויר אינו זמין"). ההרשמה חינמית
  וללא צורך בכרטיס אשראי. שימו לב: מפתח חדש עלול לקחת עד שעה-שעתיים "להתעורר"
  אצל OpenWeatherMap לפני שהוא מתחיל לעבוד בפועל.

## התקנה והרצה

```bash
# 1. התקנת חבילות
npm install

# 2. יצירת קובץ קונפיגורציה מקומי
cp .env.example .env
# פתחו את .env ומלאו: MONGODB_URI (אם לא ברירת המחדל), SESSION_SECRET,
# WEATHER_API_KEY, WEATHER_CITY_HE (שם התצוגה בעברית של עיר מזג האוויר)

# 3. ודאו ש-MongoDB רץ (mongod / Atlas)

# 4. הזנת נתוני הדגמה (כ-500 כתבות, משתמשים, תגובות, נתוני צפייה)
npm run seed

# 5. הרצת השרת
npm start
# האתר זמין בכתובת http://localhost:3000
```

לפיתוח שוטף אפשר `npm run dev` (מפעיל מחדש את השרת אוטומטית בכל שינוי, בעזרת
`node --watch`).

**מתי צריך להפעיל מחדש את השרת (`npm start`) ומתי מספיק רענון דפדפן:**
שינוי בקובצי `views/*.ejs`, `public/css/style.css` או `public/js/*.js` נטען
מחדש בכל בקשה - מספיק רענון דפדפן (Cmd/Ctrl+Shift+R לרענון קשיח). שינוי
בקובצי `server.js`, `routes/*`, `controllers/*`, `models/*`, `middleware/*`
או ב-`.env` נטען רק פעם אחת בהפעלת התהליך - חובה `Ctrl+C` ואז `npm start`
מחדש כדי שהשינוי ייכנס לתוקף.

|--------------|-------|
| `reporter1`–`reporter4` | כתב |

## סיכום פונקציונליות

- **פיד חדשות** (`/`) - גלילה אינסופית (IntersectionObserver), חיפוש, סינון
  לפי קטגוריה ו/או "לא נצפה" (מבוסס localStorage בצד הלקוח), מיון לפי תאריך/
  פופולריות. כל כרטיס מציג כותרת, תמונה, תקציר, קטגוריה, **שם הכתב** ותאריך.
  הכל דרך `/api/articles` ללא רענון עמוד.
- **עמוד כתבה** (`/articles/:id`) - מרונדר בשרת (EJS) כך שהתוכן המלא מופיע
  ב-HTML הראשוני (SEO), עם תגובות (הוספה ללא רענון) ומגבלת ספאם. עורך מחובר
  רואה גם כפתורי עריכה/מחיקה על כל תגובה (מודרציה).
- **התחברות** (`/login`) - כתבים/עורכים בלבד, session מבוסס MongoDB
  (`connect-mongo`) כדי ש-restart של השרת לא ינתק משתמשים מחוברים.
- **אזור הכתב** (`/reporter`) - יצירה/עריכה עם שמירה אוטומטית (autosave),
  שליחה לאישור, עריכת כתבה שהוחזרה או שכבר פורסמה.
- **אזור העורך** (`/editor`) - סינון לפי מצב עם עימוד, עריכה (רק לכתבה
  שממתינה לאישור), אישור ופרסום, החזרה עם הערה, מחיקה. דף הבדיקה מציג גם את
  הגוף המפורסם הנוכחי לצד התוכן החדש, להשוואה. כל מעברי המצב נאכפים בצד
  השרת (`utils/constants.js` → `ALLOWED_TRANSITIONS`).
- **ניהול משתמשים** (`/editor/users`) - יצירה, עריכת שם תצוגה/סיסמה, ומחיקה
  של חשבונות כתבים (חסום אם לכתב יש כתבות משויכות, כדי לא ליצור רשומות יתומות).
- **Impact Analytics** (`/editor/stats`) - גרף Chart.js של צפיות לאורך זמן עם
  סימון נקודות פרסום/עדכון.
- **ווידג'ט מזג אוויר** - בסיידבר, דרך proxy בצד השרת ל-OpenWeatherMap, עם
  מטמון של 15 דקות. שם העיר מוצג בעברית (`WEATHER_CITY_HE`) בנפרד מהשאילתה
  שנשלחת בפועל ל-API (שחייבת להיות באנגלית).
- **תמונות מותאמות-קטגוריה** - תמונת הדגמה של כל כתבה נבחרת לפי הקטגוריה שלה
  (ספורט/כלכלה/טכנולוגיה וכו') ולא לגמרי אקראית, כדי שהתמונה תהיה רלוונטית
  לתוכן (ראו `scripts/seed.js`).
- **אבטחה** - סיסמאות מוצפנות (bcrypt, לא ניתנות לשחזור), כל בדיקות ההרשאה
  בצד השרת, הגנת CSRF-בסיסית דרך SameSite cookies, קלט מנוקה/מוגבל אורך,
  בריחת תווי regex מיוחדים בחיפוש חופשי.

## עמודי מדיניות ונגישות

בפוטר האתר קיימים שלושה עמודים סטטיים (`routes/legalRoutes.js`,
`views/legal/`): **מדיניות פרטיות** (`/privacy`), **תקנון האתר** (`/terms`)
ו**הצהרת נגישות** (`/accessibility`) - המפרטת בכנות את התאמות הנגישות שיושמו
בפועל (HTML סמנטי, RTL, תוויות טפסים, ניווט מקלדת) לצד מגבלות ידועות, בלי
הצהרת תאימות מלאה שאינה נכונה.

## החלטות עיצוב חשובות

תהיו מוכנים להסביר את אלה בהגנה - הן התשובה לשאלות ה"למה" הכי סבירות:

1. **מבנה כתבה כפול (`content` + `published`)** - כתבה שומרת את התוכן שבעבודה
   בנפרד מ"תמונת המצב" הפומבית שהציבור רואה. כך אפשר לערוך כתבה שכבר פורסמה
   מבלי שהשינויים ייראו לציבור לפני אישור עורך (ראו `models/Article.js`).

2. **צבירת צפיות ב"דליים" של שעה, לא מסמך לכל צפייה** (`models/ViewStat.js`) -
   עם אלפי קוראים במקביל, מסמך נפרד לכל צפייה היה יוצר עומס כתיבה ואחסון
   עצום. במקום זה, כל צפייה מבצעת `$inc` אטומי על מסמך "דלי" שעתי אחד לכל
   כתבה. כך מספר המסמכים גדל לכל היותר ב-24 בשעה לכל כתבה, ללא קשר לכמות
   הצפיות בפועל - וזו בדיוק התשובה לשאלה "איך תתמכו באלפי קוראים במקביל".

3. **Session מבוסס MongoDB** (`connect-mongo`) - עונה במדויק על הדרישה
   ש-restart של השרת לא ינתק משתמשים מחוברים, כי ה-session נשמר במסד הנתונים
   ולא בזיכרון התהליך.

4. **הגבלת תגובות (sliding window בזיכרון)** - `middleware/commentRateLimiter.js`
   שומר לכל מכשיר את חותמות הזמן של תגובותיו האחרונות ובודק שלא עברו 3 בדקה.
   פתרון בזיכרון מספיק כאן כי מדובר בהגנת ספאם מיידית, לא בנתון עסקי.

5. **בדיקות הרשאה בצד השרת בלבד** - `middleware/auth.js` קובע הרשאות אך ורק
   לפי `req.session.user` (שנקבע בהתחברות), ולעולם לא לפי מידע מהלקוח. כל
   route רגיש עטוף ב-`requireReporter`/`requireEditor`. כך גם עריכת תוכן
   ע"י העורך (`editContent`) נעולה בשרת רק לכתבות בסטטוס "ממתינה לאישור" -
   לא מספיק שהממשק מציג את הכפתור רק שם.

6. **מפת מעברי מצב מפורשת** (`ALLOWED_TRANSITIONS`) - כל בקשת API שמנסה
   לשנות סטטוס כתבה עוברת דרך `assertTransitionAllowed`, כך שאי אפשר "לדלג"
   בין מצבים בעקיפין (למשל דרך קריאת API ישירה שמדלגת על הממשק). גם הבדיקה
   בצד הכתב (מתי מותר לו לערוך/לשלוח לאישור) נגזרת מאותה מפה משותפת ולא
   ממערך נפרד, כדי שלא יהיו שני מקורות אמת שעלולים להתפצל.

7. **יצירת כתבה חדשה היא POST ולא GET** (`routes/reporterRoutes.js`) - מכיוון
   שהפעולה יוצרת מסמך חדש במסד הנתונים (יש לה תופעת לוואי), היא לא יכולה
   להיות GET לפי סמנטיקת REST/HTTP: GET חייב להיות "בטוח" ואידמפוטנטי, כלומר
   רענון או כניסה חוזרת לאותה כתובת לא אמורים ליצור נתונים חדשים.

8. **חבילות npm שאינן Express/Mongoose/EJS** - נעשה שימוש ב-`bcryptjs`
   (הצפנת סיסמאות), `express-session` + `connect-mongo` (ניהול session),
   `cookie-parser` ו-`morgan` (לוגים). אלו כלי-עזר סטנדרטיים בעולם Express
   ולא "פריימוורק" חלופי (כמו React/Angular/Vue שנאסרו במפורש), אך אם המרצה
   שלכם מפרש את הדרישה בצורה מחמירה יותר (רק בדיוק הטכנולוגיות שנלמדו
   בכיתה) - כדאי לוודא מולו שזה מקובל, או להחליף את ניהול ה-session במימוש
   ידני (טבלת sessions ב-Mongo + עוגייה, בלי הספרייה).

## בעיות נפוצות

- **"MongoServerSelectionError" / השרת נופל מיד עם שגיאה** - כמעט תמיד
  אומר ש-MongoDB לא רץ. הריצו `mongod` (או ודאו ששירות ה-MongoDB פעיל) ונסו
  שוב.
- **ווידג'ט מזג האוויר מציג "לא זמין"** - ודאו ש-`WEATHER_API_KEY` ב-`.env`
  מוגדר עם מפתח תקין מ-OpenWeatherMap. אם המפתח נוצר לאחרונה, ייתכן שהוא
  עדיין לא הופעל אצלם (עד שעה-שעתיים) - שגיאת 401 בלוג השרת מעידה בדיוק על כך.
- **גרף האנליטיקס ריק** - ודאו שהרצתם `npm run seed`, ושבחרתם כתבה שאכן
  פורסמה (לכתבות בסטטוס "בהכנה"/"ממתינה" אין עדיין נתוני צפייה).
- **שינוי בקוד השרת (controller/route/model) לא נכנס לתוקף** - חובה להפעיל
  מחדש (`Ctrl+C` ואז `npm start`); בניגוד ל-views/CSS/JS שנטענים מחדש בכל בקשה.
